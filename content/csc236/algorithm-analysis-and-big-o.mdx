Before you can choose the right algorithm for a job, you need a way to measure how good an algorithm actually is. Running it on your laptop and timing it doesn't work — a faster computer will give you a different result. What you really want to know is: **as the input gets larger, how does the work grow?** That question is what algorithm analysis answers.

---

## What Is an Algorithm?

An algorithm is a **finite sequence of well-defined instructions** that takes some input, performs a series of computational steps, and produces a correct output in a finite amount of time.

Five properties every valid algorithm must have:

| Property | Meaning |
|---|---|
| **Input** | Zero or more well-defined inputs |
| **Output** | At least one result produced |
| **Definiteness** | Every step is precisely defined |
| **Finiteness** | The algorithm must eventually stop |
| **Effectiveness** | Every step is basic enough to be carried out |

A correct algorithm **halts** for every valid input and returns the correct answer. An incorrect algorithm might loop forever or return wrong results — but even incorrect algorithms are sometimes deliberately used when error rates can be controlled (randomised algorithms).

---

## Why Analyse Algorithms?

Measuring speed in seconds depends on your hardware. Two machines running the same algorithm can produce wildly different times. Instead, we count **basic operations** (comparisons, assignments, arithmetic steps) and express that count as a **function of input size n**.

Three goals of algorithm analysis:

1. **Predict performance** — estimate how the algorithm will behave on large inputs
2. **Compare alternatives** — choose between two solutions objectively
3. **Understand scalability** — know when an algorithm will stop being practical

## Mathematical Foundations

### 1. Growth Functions

When we say input size is **n**, we express running time as T(n). The shape of that function tells us everything.

### 2. Summations — Counting Loop Operations

When a loop runs from 1 to n:

<FormulaBlock
  formula="1 + 2 + 3 + \cdots + n = \frac{n(n+1)}{2}"
  label="Sum of first n integers"
/>

**Example:** if n = 5, the sum is 1+2+3+4+5 = 15. Check: 5×6/2 = 15. ✓

This formula appears whenever you have a triangular nested loop (inner loop runs 1, then 2, then 3... times per outer iteration).

### 3. Geometric Series

When each term doubles:

<FormulaBlock
  formula="1 + 2 + 4 + \cdots + 2^k = 2^{k+1} - 1"
  label="Geometric series sum"
/>

This appears in divide-and-conquer algorithms where you split the problem in half at each step.

### 4. Logarithms

A logarithm answers: "how many times must I divide n by b to reach 1?"

<FormulaBlock
  formula="\log_b a = c \iff b^c = a"
  label="Logarithm definition"
/>

**Example:** log₂ 8 = 3 because 2³ = 8.

**Why logs matter:**
- Binary Search → O(log n) — each step eliminates half the data
- Merge Sort → O(n log n) — divides problem at each level
- Balanced trees → height is log n

Logs grow **very slowly** — a sorted list of 1 billion items needs only about 30 comparisons with binary search.

## Asymptotic Notation — The Three Main Tools

Asymptotic analysis describes how running time behaves as n → ∞. We use three notations.

<DiagramBlock chart={`graph LR
    A["T(n)"] --> B["Upper bound: Big-O O(f(n))"]
    A --> C["Exact growth: Theta(f(n))"]
    A --> D["Lower bound: Omega(f(n))"]
`} />

### Big-O Notation — Worst Case

**O(f(n))** means the algorithm's running time grows **no faster** than f(n). It is a guarantee: no matter how bad the input, the algorithm will not be slower than this.

> "Even in the worst situation, the algorithm will not be slower than O(f(n))."

**Example:** Linear Search on n elements — worst case is checking every element → O(n).

### Theta Notation — Exact Growth

**Θ(f(n))** means the running time grows **exactly like** f(n) — the upper and lower bounds are the same.

**Example:** A loop that always runs exactly n times → Θ(n). No matter the input, it is precisely linear.

### Omega Notation — Best Case

**Ω(f(n))** means the algorithm takes **at least** this long. It is the best possible scenario.

**Example:** Linear Search finding the element at the very first position → Ω(1). Best case: one comparison.

## Common Complexity Classes

From fastest to slowest:

<FormulaBlock
  formula="O(1) < O(\log n) < O(n) < O(n \log n) < O(n^2) < O(2^n)"
  label="Efficiency order — left is faster"
/>

| Class | Name | Example | Behaviour |
|---|---|---|---|
| O(1) | Constant | Array index access | Same speed regardless of n |
| O(log n) | Logarithmic | Binary Search | When input doubles, work increases slightly |
| O(n) | Linear | Loop through a list | Doubles when input doubles |
| O(n log n) | Linearithmic | Merge Sort | Efficient for large datasets |
| O(n²) | Quadratic | Nested loops | Input doubles → time quadruples |
| O(2ⁿ) | Exponential | Recursive brute-force | Input grows slightly → time explodes |

<Analogy>
Imagine searching for a name in a phonebook. O(1) means you instantly know exactly which page. O(log n) means you keep dividing the book in half each time. O(n) means you check every name one by one from the start. O(n²) means you compare every name with every other name. O(2ⁿ) means you try every possible combination of names — completely impractical for large inputs.
</Analogy>

## How to Identify Complexity by Inspection

Look at the code structure:

| Structure | Complexity |
|---|---|
| Single statement | O(1) |
| One loop, 1 to n | O(n) |
| Nested loops (both 1 to n) | O(n²) |
| Loop that divides by 2 each step | O(log n) |
| Outer loop + inner divide-by-2 | O(n log n) |
| Recursive calls that branch | Often O(2ⁿ) |

## Constructive Analysis — The Step-Count Method

This is the formal technique your lecturer uses. You count **every operation** with its cost.

**Operation costs assumed in this course:**

| Operation | Cost |
|---|---|
| Addition / Subtraction | 1 |
| Multiplication / Division | 2 |
| Logical Comparison | 1 |
| Array access | 1 |
| Assignment | 1 |
| Modulus (%) | 2 |

### Worked Example 1 — Single Loop

```c
// Average of array — step-count analysis
sum = 0;           // assignment: 1 step, runs 1 time
count = 0;         // assignment: 1 step, runs 1 time
// loop overhead: i=1 (1) + test n+1 times + increment n times = 2n+2
for (i = 1; i <= n; i++) {
  sum = sum + A[i]; // add(1) + array(1) + assign(1) = 3, runs n times
}
average = sum / n;  // divide(2) + assign(1) = 3, runs 1 time
```

**T(n) = 1 + 1 + (2n+2) + 3n + 3 = 5n + 7**

Dominant term: **5n** → Time complexity: **O(n)**

### Worked Example 2 — Nested Loops

```c
// Count matching pairs — nested loop analysis
count = 0;                     // 1 step, once
// outer loop overhead: 2n+2
for (i = 1; i <= n; i++) {
  // inner loop overhead: n*(2n+2) = 2n²+2n
  for (j = 1; j <= n; j++) {
    if (A[i] == A[j])          // compare(1) + 2 array accesses(2) = 3, n² times
      count = count + 1;       // add(1) + assign(1) = 2, n² times worst case
  }
}
print count;                   // 1 step, once
```

**T(n) = 1 + (2n+2) + (2n²+2n) + 3n² + 2n² + 1 = 7n² + 4n + 4**

Dominant term: **7n²** → Time complexity: **O(n²)**

### Worked Example 3 — Two Separate Loops

```c
// Two-pass analysis: sum then count above-average
sum = 0;           // 1
count = 0;         // 1
for (i = 1; i <= n; i++)      // first loop overhead: 2n+2
  sum = sum + A[i];            // cost 3 per iteration: 3n total
average = sum / n;             // cost 3, once
for (i = 1; i <= n; i++)      // second loop overhead: 2n+2
  if (A[i] > average)          // compare(1) + array(1) = 2 per iteration: 2n
    count = count + 1;         // cost 2 per iteration: 2n worst case
print average;                 // 1
print count;                   // 1
```

**T(n) = 1+1+(2n+2)+3n+3+(2n+2)+2n+2n+1+1 = 11n + 11**

Dominant term: **11n** → Time complexity: **O(n)**

### Worked Example 4 — Logarithmic Loop

```c
// Doubling loop — runs log₂(n) times
i = 1;
while (i <= n) {
  print(i);
  i = 2 * i;  // i takes values: 1, 2, 4, 8, 16...
}
```

The loop runs while i ≤ n. Since i doubles each time, after k iterations i = 2^k. The loop stops when 2^k = n, so **k = log₂(n)**.

**T(n) = log n** → Time complexity: **O(log n)**

## Key Simplification Rules

When you have a running time function T(n):

1. **Ignore constants:** 5n → O(n)
2. **Ignore lower-order terms:** n² + n + 5 → O(n²)
3. **Focus on the dominant term** — it determines asymptotic growth

**Examples:**
- T(n) = 4n² + 3n + 2 → **O(n²)**
- T(n) = 7n + 6 → **O(n)**
- T(n) = 100 → **O(1)**
- T(n) = 2n log n + 5n → **O(n log n)**

## Practice Problem (From Course Notes)

Perform constructive analysis on this algorithm. Assume operation costs from the table above.

```
sum = 0
count = 0
for i = 1 to n
  sum = sum + A[i]
  if A[i] % 2 == 0
    count = count + 1
average = sum / n
print average
print count
```

**Solution:**

| Block | Cost per exec | Frequency | Total |
|---|---|---|---|
| sum = 0 | 1 | 1 | 1 |
| count = 0 | 1 | 1 | 1 |
| Loop overhead | — | 2n+2 | 2n+2 |
| sum = sum + A[i] | 3 | n | 3n |
| A[i] % 2 == 0 | 3 | n | 3n |
| count = count + 1 | 2 | n (worst case) | 2n |
| average = sum / n | 3 | 1 | 3 |
| print × 2 | 1 each | 1 each | 2 |

**T(n) = 1+1+(2n+2)+3n+3n+2n+3+2 = 10n + 9**

Dominant term: **10n** → **O(n)**

<Takeaway>
Algorithm analysis measures how running time grows as input size increases — not the actual seconds on a clock. Big-O is the worst-case upper bound, Theta is the exact growth rate, and Omega is the best-case lower bound. The step-count method gives you the precise T(n); asymptotic simplification rules then reduce it to its complexity class. The key principle: ignore constants and lower-order terms — only the dominant term matters.
</Takeaway>

<ExamTip>
Lecturers test this topic in three main ways. First, "identify the time complexity of this code" — look for nested loops (O(n²)), single loops (O(n)), halving loops (O(log n)), and constant-time operations (O(1)). Second, full step-count questions with specific operation costs — use the operation cost table from the course exactly, do not guess. Third, "which algorithm is more efficient?" — compare complexity classes using the efficiency order. Common traps: forgetting to drop the constant multiplier after step-count, and mixing up O (worst case) with Ω (best case).
</ExamTip>
