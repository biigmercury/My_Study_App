Searching is one of the most common operations in computing. Every time you look up a contact, filter a list, or query a database, a searching algorithm is running under the hood. This topic covers the two fundamental searching algorithms in your course: **Linear Search** (simple but works on anything) and **Binary Search** (fast but requires sorted data).

---

## What Are Searching Algorithms?

A searching algorithm finds a **specific element** (the target or key) within a collection of data — such as an array, list, or database. It determines:

1. Whether the element **exists** in the collection
2. If it does, **where** it is (its position/index)

Different searching algorithms make different trade-offs between simplicity and speed. The best choice depends on whether your data is sorted and how large it is.

---

## 1. Linear (Sequential) Search

### The Idea

Linear Search is the simplest possible approach: **scan every element from the beginning** until you find the target or reach the end of the list. No assumptions about order — it works on both sorted and unsorted data.

### Procedure

1. Start from the first element (index 0)
2. Compare the current element with the target key
3. If they match, return the index — **found**
4. If they do not match, move to the next element
5. Repeat until found or the list ends
6. If the end is reached without a match, return −1 — **not found**

### Pseudocode

```
Algorithm LinearSearch(A, n, key):
Begin
  for i = 0 to n-1 do
    if A[i] = key then
      return i          // element found at index i
    end if
  end for
  return -1             // element not found
End
```

### Worked Example

Array: **A = [12, 7, 25, 9, 15]** Search for key = **9**

| Step | Index Checked | Value | Result |
|---|---|---|---|
| 1 | 0 | 12 | 12 ≠ 9, continue |
| 2 | 1 | 7 | 7 ≠ 9, continue |
| 3 | 2 | 25 | 25 ≠ 9, continue |
| 4 | 3 | 9 | 9 = 9, **found** |

**Result:** Element 9 is found at index **3**. ✓

### C Implementation

```c
// Linear Search — C implementation
#include <stdio.h>

int main() {
    int score[10], i, search, found = 0;

    // Read array data from user
    for (i = 0; i < 10; i++) {
        printf("Enter data at location %d: ", i + 1);
        scanf("%d", &score[i]);
    }

    printf("Enter the value to search for: ");
    scanf("%d", &search);

    // Linear scan — check every element
    for (i = 0; i < 10; i++) {
        if (score[i] == search) {
            printf("Data found at position %d\n", i + 1);
            found = 1;
            break; // stop as soon as found
        }
    }

    if (found == 0)
        printf("Data does not exist in the array\n");

    return 0;
}
```

### Complexity Analysis

| Case | Condition | Comparisons | Complexity |
|---|---|---|---|
| Best | Target is at index 0 | 1 | O(1) |
| Average | Target is in the middle | n/2 | O(n) |
| Worst | Target at last position or absent | n | O(n) |

**Explanation of best case (O(1)):** In the absolute best case, the very first element is the target — only one comparison is made, regardless of how large n is.

**Explanation of worst/average case (O(n)):** We must scan through the entire array (n elements). If the target is missing, we always make exactly n comparisons.

### Real-World Applications

Linear Search is practical when:
- **Small datasets** — the overhead of sorting isn't worth it
- **Unsorted data** — data arrives in no particular order
- **One-time lookup** — sorting and binary searching is only efficient if you search repeatedly
- **Log file scanning** — checking if a value exists in a text file
- **Sensor streams** — checking if a number exists in real-time data

## 2. Binary Search

### The Idea

Binary Search is dramatically faster than Linear Search — but it only works on **sorted** data. The key insight: if the data is sorted, you can **eliminate half the remaining elements** with each comparison instead of just one.

Each step asks: "Is the target in the left half or the right half?" — then discards the wrong half and repeats on the remaining portion.

### Procedure

1. Set `low = 0` (start of array), `high = n−1` (end of array)
2. While `low ≤ high`:
   a. Calculate `mid = (low + high) / 2`
   b. If `A[mid] = key` → **found**, return mid
   c. If `A[mid] < key` → target is in right half, set `low = mid + 1`
   d. If `A[mid] > key` → target is in left half, set `high = mid - 1`
3. If loop ends without finding: return −1 — **not found**

### Pseudocode

```
Algorithm BinarySearch(A, n, key):
Begin
  low = 0
  high = n - 1
  while low <= high do
    mid = (low + high) / 2
    if A[mid] = key then
      return mid          // found at middle
    else if A[mid] < key then
      low = mid + 1       // search right half
    else
      high = mid - 1      // search left half
    end if
  end while
  return -1               // not found
End
```

### Worked Example

Sorted array: **A = [5, 12, 18, 21, 30, 42, 56]** (n=7) Search for key = **30**

| Step | low | high | mid | A[mid] | Decision |
|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 21 | 30 > 21 → search right, low = 4 |
| 2 | 4 | 6 | 5 | 42 | 30 < 42 → search left, high = 4 |
| 3 | 4 | 4 | 4 | 30 | 30 = 30 → **found** at index 4 |

**Result:** Element 30 found at index **4** in only 3 comparisons (vs 5 comparisons needed for linear search). ✓

### Second Worked Example — Not Found

Sorted array: **A = [5, 12, 18, 21, 30, 42, 56]** Search for key = **20**

| Step | low | high | mid | A[mid] | Decision |
|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 21 | 20 < 21 → search left, high = 2 |
| 2 | 0 | 2 | 1 | 12 | 20 > 12 → search right, low = 2 |
| 3 | 2 | 2 | 2 | 18 | 20 > 18 → search right, low = 3 |
| 4 | 3 | 2 | — | — | low > high → **not found** |

**Result:** −1 (20 is not in the array). Confirmed in just 3 comparisons.

### Why Binary Search is O(log n)

Each comparison eliminates half the search space:

<FormulaBlock
  formula="n \to \frac{n}{2} \to \frac{n}{4} \to \frac{n}{8} \to \cdots \to 1"
  label="Search space reduction at each step"
/>

After k steps, the remaining size is n/2^k. The search ends when n/2^k = 1, which means:

<FormulaBlock
  formula="2^k = n \implies k = \log_2 n"
  label="Number of steps in Binary Search"
/>

So Binary Search makes at most **log₂ n** comparisons — regardless of whether the element is found.

### Complexity Analysis

| Case | Condition | Complexity |
|---|---|---|
| Best | Target is at the exact midpoint on first try | O(1) |
| Average | Target found after several halvings | O(log n) |
| Worst | Target absent or at extremes | O(log n) |

Binary search dramatically outperforms linear search at scale:

| n | Linear (worst) | Binary (worst) |
|---|---|---|
| 100 | 100 | 7 |
| 1,000 | 1,000 | 10 |
| 1,000,000 | 1,000,000 | 20 |
| 1,000,000,000 | 1,000,000,000 | 30 |

### Loop Invariant Correctness Proof

**Loop Invariant:** At the start of each iteration, if the key exists in A, it lies within the subarray **A[low..high]**.

- **Initialization:** Before the first iteration, A[0..n-1] is the entire array. If key exists anywhere, it is in this range. ✓
- **Maintenance:**
  - If A[mid] < key: key must be in A[mid+1..high]. We set low = mid+1. Invariant preserved.
  - If A[mid] > key: key must be in A[low..mid-1]. We set high = mid-1. Invariant preserved.
- **Termination:** Loop ends when low > high (empty range). Invariant says key is in A[low..high] — but this range is empty, so key is not present. Return -1 is correct. ✓

### Real-World Applications

- **Sorted databases** — finding records by indexed key
- **Dictionary/phonebook search** — alphabetically sorted entries
- **Library catalogue** — books sorted by catalog number
- **Version control** — git bisect uses binary search to find which commit introduced a bug
- **Autocomplete systems** — searching sorted word lists
- **Computer graphics** — searching sorted coordinate lists

## Comparison: Linear vs Binary Search

| Feature | Linear Search | Binary Search |
|---|---|---|
| Data requirement | Sorted or unsorted | Must be sorted |
| Best case | O(1) | O(1) |
| Average case | O(n) | O(log n) |
| Worst case | O(n) | O(log n) |
| Implementation | Very simple | Moderate |
| Memory | O(1) | O(1) |
| Use case | Small/unsorted data | Large sorted data |

<Analogy>
Linear Search is like searching for a word in a novel by reading every page from the beginning. Binary Search is like searching for a word in a dictionary — you open to the middle, decide whether your word comes before or after, discard half the dictionary, and repeat. You never check pages you know cannot contain your word. For a 1000-page dictionary, linear search might take 1000 page checks; binary search takes at most 10.
</Analogy>

<Takeaway>
Linear Search scans every element and works on any data — O(n) worst case. Binary Search repeatedly halves the search space and achieves O(log n), but requires sorted input. For small or unsorted datasets, use linear search. For large sorted datasets, binary search is far more efficient. The logarithmic reduction in Binary Search (n → n/2 → n/4 → ... → 1) is the key insight that drives its O(log n) complexity.
</Takeaway>

<ExamTip>
Examiners typically ask: (1) trace Binary Search step by step for a given sorted array — show all values of low, high, and mid at each step; (2) state time complexities — remember Binary Search is O(log n) average AND worst case, not just average; (3) loop invariant proof for Binary Search — the invariant is "if key exists, it is within A[low..high]"; (4) "why can't you use Binary Search on a linked list?" — because it requires random access (calculating mid by index), which linked lists do not support efficiently; (5) compare the two algorithms for a given scenario — justify which one to use and why.
</ExamTip>
